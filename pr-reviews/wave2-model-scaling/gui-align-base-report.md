# ReShiki local real-app check

Build under test: main `1d94f392` (before), release build, as supplied. Date: 2026-11-15 (Asia/Tokyo).

Wrapper: `<base build>/ReShiki.app`.
Input: `gallery-64.rsk`, supplied as 64 shortcut galleries side by side (30,912 atoms).

The check found a visible selection followed by prolonged unresponsiveness after Align left edges. Align, undo, and nudge did not produce their required responsive results within their five-minute allowances. The canvas later became blank. Graceful quit also failed, and the authorized wrapper-path termination was used. The hover test could not be performed with the available computer-use controls.

## Setup and method

The exact requested `open -n -a` command launched the wrapper with the input file. After waiting, `pgrep -fl pr-model-scaling-base/app` showed one wrapper process, PID 29352, and computer use attached by the exact wrapper path. No additional instance was launched. The data-directory environment was not changed, the window was not resized, no other apps were driven, and no repository files were edited.

All GUI actions used computer use. PNG captures contain only the ReShiki window. After computer-use screenshot/accessibility timeouts, the explicitly permitted `screencapture -l 74144` fallback was used. The first four saved computer-use captures arrived JPEG-encoded and were converted to actual PNG without changing the depicted content. All saved screenshot files were then checked for PNG format. Supplementary captures are saved as `*-poll-*.png`; all successfully captured screenshots are in this directory.

Each timed key command was preceded by a shell wall-clock timestamp. Reported times run from that timestamp to the observed result or deadline capture. Tool round trips, attachment, and the required 20-second timeout retry waits affect observation times. Values marked **≤** are observation upper bounds, not precise internal application latency. During the extended waits, fallback screenshots were generally captured about every 5–6 seconds, with occasional longer intervals. Unchanged fallback images were checked by their PNG hashes as well as visual review of the relevant states.

## Late canvas change

The final nudge screenshot at roughly 313 seconds after the Down attempt still matched the frozen selected row. The first later fallback screenshot, `06-hover.png`, showed the blank modified drawing window at roughly **381 seconds after the Down attempt** and **1,032 seconds after the align attempt**. This late change occurred after the required five-minute step deadlines. There was no successful accessibility check establishing which pending command had completed, so it is not attributed to alignment, undo, nudge, or clearing selection. No visible pileup at the left or restored row was verified.

## Friction

- **Fit drawing:** The displayed zoom rounds to 0%, the structures are extremely small, and repeated content meets both horizontal canvas boundaries. This makes the whole-drawing extent and individual copies difficult to inspect.
- **Select All:** The initial computer-use call timed out before the result could be verified. A retry wait was needed, which delayed verification and reduced timing precision.
- **Align, undo, and nudge:** The previous selected row remained visible across each five-minute allowance while computer-use observations timed out. The captured window showed no progress indication, making it difficult to distinguish a long-running operation from a stalled editor.
- **Late redraw:** The canvas eventually became blank while the inspector still displayed selection counts and the status said “Drawing changed.” The visible state did not explain where the drawing had gone or which action had completed.
- **Quit:** Cmd+Q did not close the app within 60 seconds and no save prompt was observed. The supplied process-termination fallback was required to finish the session.
- **Test tooling:** During the selection-clear attempt, computer use reported `noWindowsAvailable` even though a process query and the permitted window capture still found the app. This prevented reliable confirmation of that click. The documented computer-use controls also lacked hover-only pointer movement, preventing the requested hover measurement.

## Could not complete and why

- Could not independently verify all 64 copies or inspect individual chemical structures at the fitted 0% scale; the row meets/clips the canvas boundaries.
- Could not verify the expected left-edge pileup, undo restoration, or nudge movement with a responsive editor within the five-minute allowances. After the align attempt, action calls and accessibility observations repeatedly timed out. Timed-out key calls do not establish exactly when or whether the application accepted each key.
- Could not perform the five-second hover-only sweep or capture the pointer over a structure because the available computer-use API has no documented pointer-move/hover method. `06-hover.png` is a truthful capture of the actual step state; it is not hover evidence.
- Could not provide approximately ±2-second application-completion measurements for launch/selection because attachment and timeout retry waits left gaps between observations. The report gives observed upper bounds instead. For the long-running steps, it establishes that the expected responsive result was not verified within five minutes.
- Could not quit normally or choose “Don’t Save,” because no save prompt was observed and Cmd+Q did not close the app. The explicitly authorized fallback terminated the wrapper; the final process check confirmed it was no longer running.
